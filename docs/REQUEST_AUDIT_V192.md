# Промысел v1.92 — аудит маршрутов запросов и уменьшение сетевой нагрузки

## Область и доказательства

Проверены активные GitHub Flutter-сборки Web и архивный Android-рецепт, клиентская авторизация, регистрация, персонал, присутствие, синхронизация, чаты, устройство уведомлений, а также маршруты Supabase и агрегированная история Edge Function по последним доступным журналам.

В доступной выборке HTTP запросов: `sync/pull` — 293 успешных GET и 105 HTTP 500; `chat/rooms` — 248 успешных GET и 23 HTTP 500; `presence` — 197 GET; `registration/fields` — 216 GET; `registration/pending` — 120 GET и 7 HTTP 403; `device-push/deliver` — 149 успешных POST. Числа из прошлых логов, не показатель после релиза.

## Безопасные изменения в клиенте

- Список заявок запрашивается только у администратора и начальника цеха; убраны лишние запросы от операторов и других ролей. Кэш привязан к текущему пользователю и месторождению.
- Повторные одновременные запросы списка заявок объединены, добавлен 20-секундный период повторного использования. При ручном обновлении, одобрении или отклонении заявки используется принудительное обновление.
- Список месторождений на обычном экране входа не запрашивается: он нужен только при открытии регистрации. Параллельные запросы объединены; двухминутный кэш обходится при изменении месторождения.
- Список присутствия сотрудников использует общий механизм и его TTL, а не повторный принудительный запрос с главной, профиля и списка персонала.
- Фоновый интервал синхронизации увеличен с 90 до 150 секунд, но ручные действия и реальные локальные изменения по-прежнему инициируют синхронизацию; слушатели состояния не дублируются при повторной инициализации и освобождаются при dispose.
- Рутинный запуск доставки push после успешного pull ограничен по пользователю/месторождению (не чаще раза в 3 минуты), что сокращает пустые вызовы `/deliver`. Для событий, требующих немедленных уведомлений, нужна отдельная событийная очередь, а не вызов после любого pull. Это остаётся отдельной архитектурной задачей.

## Ограничения, которые нельзя исправлять локальным обходом

- `sync_events`: 133 `app_state` записи (средний payload 184 КБ, максимальный 447 КБ), 8 `measurement` (~1,3 КБ). В `app_state` смешаны участки, кусты, задания, обучение, графики, аватары и уведомления. Серверная функция `effectiveState` объединяет только 4 последних снимка. **Нельзя** отправлять по одному неполному снимку каждого раздела: данные других разделов могут потеряться. Безопасное разделение требует версионированных, предметных событий, обратной совместимости и тестов восстановления.
- Серверный `sync/pull` ранее возвращал HTTP 500 и мог работать десятки секунд; `chat/rooms` тоже возвращал 500. Изменения v1.92 уменьшают лишние запросы, но не устраняют серверный сбой и не являются доказательством исправления задержек.
- Сетевые запросы `OPTIONS` — нормальные CORS preflight, их нельзя механически считать дублями GET/POST.
- Разделы чатов и регистрации используют собственные API. Не переносили их данные в промысловый `sync/push`. База Supabase и роли не изменены.
- Производственная безопасность: нет массовых изменений, удаления данных, применения SQL/Edge Function и автоматической сборки APK.

## Контроль

Скрипты `tools/prepare_promysel_request_optimizer_v192.py` и `tools/test_promysel_request_optimizer_v192.py` включены одновременно в Web и архивный Android-рецепт. Клиентские regression checks выполняются **после** подготовки источников v1.91, до Flutter analyze/test/build. Если сборка, тесты либо Cloudflare DEV завершатся ошибкой, публикация PROD блокируется. Для проверки производительности нужны замеры после релиза по идентичной нагрузке и сквозные тесты на нескольких устройствах.
