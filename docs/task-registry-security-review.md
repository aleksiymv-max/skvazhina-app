# Канонический реестр заданий и защищённые фотографии — проект для staging

**Статус: НЕ ПРИМЕНЯТЬ В PRODUCTION.** SQL в `supabase/staging/20261102_task_registry_evidence_review_only.sql` хранится вне `supabase/migrations`, чтобы не выполняться автоматически.

## Зачем нужен отдельный реестр
Сейчас `WorkTaskStore` хранит задания в синхронизируемом `app_state` JSON. Клиентские проверки ролей не защищают от прямого изменения JSON. Нельзя выдавать подписанные ссылки или разрешать запись фотографий по произвольному `taskId`.

Проект предлагает таблицы `work_tasks`, `work_task_events`, `task_evidence`, приватный Storage bucket и серверные RPC для выполнения/подтверждения. Автор, месторождение, назначение и статус проверяются по реальным `field_memberships` (approved=true, blocked=false), а не по данным клиента.

## Дополнительные ограничения безопасности (02.11.2026)
- Для общих заданий действует явный список получателей `work_task_assignees`, а не автоматический доступ всех операторов месторождения.
- RLS назначения использует квалифицированные `work_task_assignees.field_id`, `work_task_assignees.task_id`, `work_task_assignees.user_id` во вложенных запросах, чтобы исключить неоднозначность имён и межместорождённые совпадения идентификаторов.
- Серверная проверка подтверждения теперь требует действующее право `can_manage_tasks`, даже если пользователь ранее был автором задания и позднее потерял роль.
- Пока нет безопасного механизма отзыва назначения и полномасштабных PostgreSQL/RLS тестов, PR остаётся черновым.

## Перед запуском в staging
1. Создать **отдельный** Supabase-проект с той же структурой, но исключительно синтетическими пользователями и объектами.
2. Прогнать миграции production-структуры в тестовом проекте и снять backup.
3. Убедиться, что bucket `promysel-task-evidence` отсутствует; проверить существующие политики `storage.objects`.
4. Применить staging SQL только к тестовому проекту; проверить синтаксис, все RLS, права на RPC и доступность Storage.
5. Проверить `SECURITY DEFINER` с ролями `anon`, `authenticated`, `service_role`; нельзя доверять `user_metadata`.
6. Провести негативные тесты прямых PostgREST запросов (не только интерфейса).

## Обязательные E2E-сценарии (синтетические учётные записи)
- Автор с ролью engineer создаёт личное задание одобренному сотруднику своего месторождения.
- Посторонний пользователь, участник другого месторождения, неподтверждённый и заблокированный сотрудник не читают, не создают и не изменяют задания и фотографии.
- Нельзя назначить задание сотруднику другого месторождения, чужому участку или кусту.
- Оператор видит и выполняет своё задание, но не подтверждает чужое; автор и начальник цеха могут подтвердить/отклонить.
- Два повторных запроса выполнения не создают два события.
- Подтверждённое задание нельзя повторно выполнить; прямой UPDATE/DELETE таблиц запрещён.
- Подмена `field_id`, `task_id`, `uploaded_by` или `object_path` в `task_evidence` отвергается.
- Только назначенный исполнитель или явно указанный в `work_task_assignees` сотрудник общего задания может добавлять фотографию; только участники с правом просмотра задания могут скачать её.
- Сотрудник другого участка/куста того же месторождения без явного назначения не видит общее задание.
- Автор задания, потерявший роль инженера/начальника, не может подтвердить или отклонить его после изменения роли.
- Проверить Storage загрузку JPEG/PNG/WebP, лимит 10 МБ, отсутствие публичного доступа и запрет UPDATE/DELETE объектов.
- После блокировки сотрудника ранее доступная фотография перестаёт читаться по авторизованному запросу.
- При плохом интернете повторная загрузка с тем же UUID не создаёт дубликатов; проверить состояние частично загруженного объекта.
- Проверить параллельные действия двух сотрудников, отключение сети, восстановление и согласованность истории.

## Открытые архитектурные вопросы до релиза
- **Миграция существующих заданий.** Нужен проверенный backfill из `app_state` без потери старых ID, истории и авторства; не придумывать UUID авторов по имени.
- **Область общих заданий.** Добавлена таблица `work_task_assignees`: для общих заданий `area`/`pad` одного членства в месторождении недостаточно. Исполнитель получает доступ только при явном назначении на конкретное задание, проверке `approved=true`, `blocked=false` и разрешённой роли. Необходимо дополнительно реализовать отзыв назначения, сверку участка/куста с фактической областью работы сотрудника и тесты конкурентных назначений. До этих проверок выкатывать нельзя.
- **Фотографии.** Нужны очистка незавершённых загрузок, проверка реального MIME, безопасная генерация UUID и повторные попытки.
- **История.** События `work_task_events` должны синхронизироваться и отображаться в приложении, а не заменять историю в старом JSON до проверки.
- **Rollback.** Подготовить план отката с сохранением данных; после начала записей в новые таблицы нельзя просто удалять их.
- **Клиентская интеграция.** Только после успешного staging: репозиторий, очередь offline, конфликтные изменения, экран фотографий, RLS-тесты двух аккаунтов.

## Граница этой работы
Этот документ и SQL **не означают** внедрение фотографий или задач в production. Это отдельный безопасный кандидат на ревью, не связанный со слиянием PR #2 по «Истории». Публикация и применение SQL заблокированы до независимого staging/E2E и резервного плана.

## Изолированные PostgreSQL-проверки (03.11.2026)

Workflow `.github/workflows/staging-task-registry.yml` теперь поднимает одноразовый PostgreSQL 16 **без подключения к Supabase production**, применяет proposal SQL к синтетической схеме и проверяет две и более роли через настоящие PostgreSQL RLS и RPC. Фикстура: `tools/staging_task_registry_pg_fixture.sql`; сценарии: `tools/staging_task_registry_pg_checks.sql`. Тесты включают: назначение/чтение личного и общего задания, доступ к metadata Storage, отказ чужому и заблокированному пользователю, идемпотентность завершения, запрет прямого UPDATE, подтверждение руководителем, отзыв назначения и единственную запись в журнале отзыва.

Для общего задания добавлена RPC `promysel_revoke_task_assignee` с серверной проверкой актуальных прав, блокировкой строки задания, журналом `work_task_assignee_events` и повторяемым результатом без двойного события. Прямой DELETE для клиента не предоставляется. Отзыв запрещён для задания, ожидающего подтверждения или уже подтверждённого, чтобы не менять историю выполненной работы задним числом.

**Ограничение:** это тест PostgreSQL с минимальными синтетическими заглушками Auth и Storage, а не полный Supabase/PostgREST/Storage E2E. Перед production всё ещё обязательны изолированный Supabase staging, проверка настоящих политик и API, безопасный backfill legacy app_state, тесты offline, реальное устройство и план rollback. Не применять этот SQL к рабочему проекту только по результату CI.


## Конкурентный отзыв назначения и завершение (03.11.2026)

Выявлена гонка: прежняя RPC `promysel_complete_task` проверяла назначение **до** блокировки строки задания. Если руководитель успевал отозвать назначение во время ожидания блокировки, ранее допущенный запрос мог завершить задание уже после отзыва доступа.

В staging-кандидате порядок исправлен: сначала `SELECT ... FOR UPDATE`, затем актуальная проверка `app_private.can_attach_task`. Добавлен тест `tools/test_staging_task_registry_race.py`: руководитель удерживает блокировку, отзывает назначение, а параллельный запрос оператора должен завершиться отказом без события выполнения. Тест запускается в одноразовом PostgreSQL в CI. Это не является проверкой на настоящем Supabase Storage/PostgREST и не разрешает публикацию в production.

Дополнительный открытый вопрос: конкурентное **создание** назначения при одновременном завершении задания ещё требует отдельной сериализации и теста; нельзя считать все гонки закрытыми.
