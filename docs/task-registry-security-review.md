# Канонический реестр заданий и защищённые фотографии — проект для staging

**Статус: НЕ ПРИМЕНЯТЬ В PRODUCTION.** SQL в `supabase/staging/20261102_task_registry_evidence_review_only.sql` хранится вне `supabase/migrations`, чтобы не выполняться автоматически.

## Зачем нужен отдельный реестр
Сейчас `WorkTaskStore` хранит задания в синхронизируемом `app_state` JSON. Клиентские проверки ролей не защищают от прямого изменения JSON. Нельзя выдавать подписанные ссылки или разрешать запись фотографий по произвольному `taskId`.

Проект предлагает таблицы `work_tasks`, `work_task_events`, `task_evidence`, приватный Storage bucket и серверные RPC для выполнения/подтверждения. Автор, месторождение, назначение и статус проверяются по реальным `field_memberships` (approved=true, blocked=false), а не по данным клиента.

## Перед запуском в staging
1. Создать **отдельный** Supabase-проект с той же структурой, но исключительно синтетическими пользователями и объектами.
2. Прогнать миграции production-структуры в тестовом проекте и снять backup.
3. Убедиться, что bucket `promysel-task-evidence` отсутствует; проверить существующие политики `storage.objects`.
4. Применить staging SQL только к тестовому проекту; проверить синтаксис, все RLS, права на RPC и доступность Storage.
5. Проверить `SECURITY DEFINER` с ролями `anon`, `authenticated`, `service_role`; нельзя доверять `user_metadata`.
6. Провести негативные тесты прямых PostgREST запросов (не только интерфейса).

## Обязательные E2E-сценарии (синтетические учётные записи)
- Автор с ролью engineer создаёт личное задание одобренному сотруднику своего месторождения.
- Посторонний пользователь, участник другого месторождения, неподтверждённый и заблокированный сотрудник не читают, не создают и не изменяют задания и фотографии.
- Нельзя назначить задание сотруднику другого месторождения, чужому участку или кусту.
- Оператор видит и выполняет своё задание, но не подтверждает чужое; автор и начальник цеха могут подтвердить/отклонить.
- Два повторных запроса выполнения не создают два события.
- Подтверждённое задание нельзя повторно выполнить; прямой UPDATE/DELETE таблиц запрещён.
- Подмена `field_id`, `task_id`, `uploaded_by` или `object_path` в `task_evidence` отвергается.
- Только назначенный исполнитель или разрешённый сотрудник общего задания может добавлять фотографию; только участники с правом просмотра задания могут скачать её.
- Проверить Storage загрузку JPEG/PNG/WebP, лимит 10 МБ, отсутствие публичного доступа и запрет UPDATE/DELETE объектов.
- После блокировки сотрудника ранее доступная фотография перестаёт читаться по авторизованному запросу.
- При плохом интернете повторная загрузка с тем же UUID не создаёт дубликатов; проверить состояние частично загруженного объекта.
- Проверить параллельные действия двух сотрудников, отключение сети, восстановление и согласованность истории.

## Открытые архитектурные вопросы до релиза
- **Миграция существующих заданий.** Нужен проверенный backfill из `app_state` без потери старых ID, истории и авторства; не придумывать UUID авторов по имени.
- **Область общих заданий.** Текущая модель не содержит назначений сотрудников на отдельные участки/кусты. В staging разрешение на общие задания опирается на активное членство в месторождении и роль `can_walk`. До production требуется согласовать более узкую область доступа либо ввести отдельные связи.
- **Фотографии.** Нужны очистка незавершённых загрузок, проверка реального MIME, безопасная генерация UUID и повторные попытки.
- **История.** События `work_task_events` должны синхронизироваться и отображаться в приложении, а не заменять историю в старом JSON до проверки.
- **Rollback.** Подготовить план отката с сохранением данных; после начала записей в новые таблицы нельзя просто удалять их.
- **Клиентская интеграция.** Только после успешного staging: репозиторий, очередь offline, конфликтные изменения, экран фотографий, RLS-тесты двух аккаунтов.

## Граница этой работы
Этот документ и SQL **не означают** внедрение фотографий или задач в production. Это отдельный безопасный кандидат на ревью, не связанный со слиянием PR #2 по «Истории». Публикация и применение SQL заблокированы до независимого staging/E2E и резервного плана.
